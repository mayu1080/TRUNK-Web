# PRODUCT_LIST デモ方針（要約）

> CULTISH 5 解析 + 構成案 A〜E 比較の要約。最終方式は**未決定**。本番コード・content レイヤー・screen-flow は対象外。

## CULTISH 5 から読み取れること

| 観測 | 含意 |
|------|------|
| DOM + canvas 2枚、Three.js 使用の可能性大 | ハイブリッド構成。WebGL 複数は Context Lost リスク |
| `<img>` 少・画像は JS/WebGL 管理 | 40〜70枚は DOM 大量配置よりテクスチャ方式が妥当 |
| Main thread 負荷が目立つ | GPU だけでなく decode・JS・フィルタがボトルネック |
| 見た目は「強い3D」より 2.5D | 暗背景・白黒・ノイズ・パララックス・微モーションが核 |
| カクつき・音切れの印象 | 常設4面キオスクでは安定性検証が必須 |

**結論**: 構造（WebGL探索 + DOM UI）は参考にする。2 canvas・Context Lost 前提・PCカーソル演出は TRUNK にそのまま持ち込まない。

## 持ち込む / 翻訳する / 持ち込まない

| 区分 | 内容 |
|------|------|
| **持ち込む** | 暗背景・白黒高コントラスト、画像の WebGL 管理、レイヤー奥行き、粒状ノイズ、写真の出入り、操作連動の微反応、`assetIndex` 的な束ね |
| **翻訳する** | カーソル→タッチ慣性/リップル、ホバー→押下反応、ホイール→スワイプ/ピンチ、クリック→タップ→IMAGE_ZOOM、演出→数値パラメータ化 |
| **持ち込まない** | 2 canvas 併用、Pixi+Three 本格併用、Context Lost 許容、LIST 本体の動画化、外部演出アプリ常時連携、フル3D 前提 |

## 主レンダラー3案（要点）

| 案 | 強み | 弱み | 位置づけ |
|----|------|------|----------|
| **PixiJS 主** | パン/ピンチ/タップ・4面・1 canvas・保守 | 上限は Three より低い場合あり | 本番候補の基盤 |
| **Three.js 主** | 没入感・質感の上限 | 重い・4面で Context Lost リスク | **表現上限確認用**（本番第一候補ではない） |
| **Pixi + Three風演出** | 見た目と安定性のバランス | 演出チューニング工数 | **最有力候補** |

## 構成案 A〜E

| 案 | 構成 | 目的 | 本番候補 |
|----|------|------|----------|
| **A** | DOM + Motion | UI・遷移・白カードの確認 | UI層として必須 |
| **B** | Pixi + DOM + Motion | 大量画像・パン/ピンチ/タップの機能検証 | ◎ 第一案・フォールバック |
| **C** | Three + DOM + Motion | Three.jsで到達できる表現上限の確認 | △ 条件付き（第一候補ではない） |

**原則**: 探索は WebGL **1 canvas**。Pixi と Three の同一 LIST 内本格併用は避ける。UI は DOM + Motion。

## 推奨進行順

DA と DB は**並行可**だが、判断材料として **DB を優先**する。

LIST の核は以下のため、DB が最優先:

- 40〜70枚画像
- WebGL / texture 管理
- パン・ピンチズーム・タップ判定
- `assetIndex` 接続
- 1 canvas での安定性
- 4面運用の性能

## 合否基準

デモ実装時の最低合否基準。

| # | 基準 |
|---|------|
| 1 | 70枚表示で 1台 **55fps 以上** |
| 2 | 4面同時表示で **30分間クラッシュなし** |
| 3 | **WebGL Context Lost なし** |
| 4 | タッチ操作で**明確な遅延を感じない** |
| 5 | パン / ピンチズームが**破綻しない** |
| 6 | 画像タップの**誤判定が少ない** |
| 7 | `IMAGE_ZOOM` 表示時に LIST 側の操作が**暴発しない** |
| 8 | `categoryDrawer` 表示時に LIST 側の操作が**暴発しない** |
| 9 | content 差し替え後も**再実装なしで表示できる** |
| 10 | `assetIndex` + `getContentFileUrl` と**接続できる** |
| 11 | 4面運用時に GPU メモリが**過剰に増えない** |
| 12 | 画面を閉じたときに texture / sprite / listener を**適切に破棄できる** |

## 音の扱い

CULTISH 5 では音も印象に効いているが、**初期 LIST デモでは音は対象外**。

| 理由 | 内容 |
|------|------|
| 判断の複雑化 | 音があるとパフォーマンス判断が難しくなる |
| 原因切り分け | 音切れと描画カクつきの切り分けが困難 |
| 優先順位 | まず LIST 描画・タッチ・FPS・安定性を優先 |

**方針**

- 初期 LIST デモ: **音なし**
- SE / ambient: 必要なら**後工程で別検証**
- 音の本格検討: **LIST 描画方式決定後**

## 安定性リスクと対策

| リスク | 対策 |
|--------|------|
| Context Lost | 探索 canvas 1枚、復旧ハンドラ |
| Main thread 飽和 | thumb、非同期 decode、rAF 内更新 |
| GPU メモリ（4面） | 解像度上限、dispose |
| 座標ずれ | 単一 WebGL + DOM overlay |
